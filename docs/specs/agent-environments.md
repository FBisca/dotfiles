# Agent environments

Paths: install.sh, agents/.pi/, agents/.stow-local-ignore, tests/test_pi.py, tests/test_pi_acceptance.py, tests/test_pi_lens.py, docs/verification/pi-rtk.md, README.md

The dotfiles installer owns one machine's agent environments. Claude Code and Codex are configured from `agents/.claude/settings.base.json` and `agents/.codex/config.base.toml`; Pi is configured from `agents/.pi/settings.base.json`. Each one is a tracked base merged with an optional private overlay and, for Claude Code and Codex, with the live file, so the user's own keys always win. The installer never writes credentials: they stay in the tool's own credential store, in the environment or in the private overlay.

Skills are shared, not forked: the installer symlinks them into `~/.agents/skills`, which Pi discovers natively, and reports the skills it found and the ones that are missing. A missing skill is a reported prerequisite, never an invented one.

Pi reaches the `agent-runtime` server through its own user-level `mcp.json`: the installer registers the entry there (the runtime's own server path, `AGENT_RUNTIME_DISPATCH=1`, `exposure: deferred` with `report` direct, a `description` naming `spawn`, `wait` and `stop`, a 600 s timeout), keeps every other server in that file, and backs the file up before it changes it. Pi ships no permission prompt, so the tool list is not what authorizes a Pi lead: the server refuses what the host policy in `~/.config/agent-runtime/hosts.json` does not allow, and the installer reports that policy without ever writing it. The runtime writes the same entry itself before it starts a Pi worker, so the path in it always names the running runtime.

Pi's RTK optimizer is declared in the tracked base settings as the package `npm:pi-rtk-optimizer@0.9.0`, so Pi installs it at its next start and rewrites every bash command through the `rtk` binary, which prints the compact form of git, build and test output. The binary is a prerequisite this repo never installs: the installer detects it and reports the `brew install rtk` line when it is missing, and every command still runs unchanged without it.

Pi's web search is the `npm:pi-web-search-lite` package, declared in the same tracked base. It reads one JSON file of its own, `<pi agent dir>/pi-web-search-lite/config.json`: the tracked base `agents/.pi/pi-web-search-lite.config.json` holds the defaults and the installer merges it under the user's file, so the user's own values win and a rerun changes nothing. The search key is never written: the extension reads `EXA_API_KEY` from the environment, and the installer reports that prerequisite without failing when it is missing. The extension's tools are declared `deferred` and Pi's own `tool_search` is enabled, so they cost nothing until the model needs them.

Pi's real-time code feedback is the `npm:pi-lens` package, declared in the same tracked base at user scope, so it is installed for every repo instead of being declared per project. It ships disabled (`lens.enabled: false`): a four-run cross-file rename benchmark found the model never calls the LSP tools (they start lazy-inactive behind an activation loader), while background warmup and the read-before-edit guard added 38-79s and 23-96k tokens per task; `/lens-toggle` re-enables it for one session. When on, language servers follow each project's languages: the Dart server comes from the Flutter SDK on PATH, and pi-lens installs the TypeScript server once Pi trusts the project. Its global config `~/.pi-lens/config.json` is merged from the tracked base `agents/.pi/pi-lens.base.json` under the user's file, the same merge-under-live pattern as the other extension configs. The tracked stance is read-only - the `typos` spell server disabled, format, autofix and actionable-warnings autofix off - so pi-lens reports findings but never writes files outside the agent's own tools. A repo overrides any of it in its own `.pi-lens.json`, field by field; the installer writes no project files.

## Requirements

- **R1** WHEN the published Pi checklist runs on a machine with an authorised MiniMax provider, THEN a bounded edit in a disposable worktree completes without the model repeating the same tool call, and the outcome is recorded in `docs/verification/pi-bootstrap.md`. (from pi-bootstrap/S1)
- **R2** WHEN the installer runs on a machine that already has Claude Code or Codex configuration, THEN those files and the shared skill links are left unchanged, and a rerun is a no-op. (from pi-bootstrap/S2)
- **R3** WHEN Pi starts after the installation, THEN it discovers each installed managed skill by its canonical symlink, and the installer reports `start-planning` and `grilling` as ready or missing. (from pi-bootstrap/S3)
- **R4** WHEN the Pi configuration is installed, THEN no credential, subscription token or private endpoint appears in a tracked file or in the installer's output. (from pi-bootstrap/S4)
- **R5** WHEN the Pi configuration is installed, THEN Pi has the `agent-runtime` MCP server, and every mutating tool it exposes is authorized by the Pi host policy in `~/.config/agent-runtime/hosts.json`. (from pi-agent-runtime-mcp/S1)
- **R6** WHEN Pi is not installed or no credential is authorised, THEN the installer reports the missing prerequisite and picks no provider of its own. (from pi-bootstrap/S6)
- **R7** WHEN the installer sets Pi up, THEN it reports the `rtk` binary it found, or the `brew install rtk` prerequisite when it is missing, and the packages Pi will install at its next start, and a missing `rtk` never fails the install. (from pi-rtk/S1)
- **R8** WHEN Pi starts with the tracked base settings, THEN it installs the declared `pi-rtk-optimizer` package and rewrites its bash commands through `rtk`, and every command still runs unchanged when `rtk` is missing. (from pi-rtk/S2)
- **R9** WHEN the Pi configuration is installed on a machine with the agent-runtime server, THEN `~/.pi/agent/mcp.json` carries the `agent-runtime` entry - the runtime's own server path, `AGENT_RUNTIME_DISPATCH=1`, `exposure: deferred` with `report` direct, a `description` naming `spawn`, `wait` and `stop`, a 600 s timeout - and every other server in that file survives. (from pi-agent-runtime-mcp/S1)
- **R10** WHEN the installer runs again, THEN the Pi MCP file is byte for byte the same and no backup is written. (from pi-agent-runtime-mcp/S2)
- **R11** WHEN the machine has no agent-runtime server to point at, THEN the installer reports that prerequisite and writes no MCP entry. (from pi-agent-runtime-mcp/S3)
- **R12** WHEN the installer sets Pi up, THEN it reports the Pi host policy that authorizes a Pi lead, and never writes it. (from pi-agent-runtime-mcp/S4)
- **R13** WHEN the live Pi MCP file is not valid JSON, THEN it is backed up and left untouched. (from pi-agent-runtime-mcp/S5)
- **R14** WHEN the installer sets Pi up, THEN the tracked Pi base declares the `npm:pi-web-search-lite` package and enables `tool_search` through `defaultTools`, and Pi installs the package at its next start. (from pi-web-search/S1)
- **R15** WHEN the installer sets Pi up, THEN `~/.pi/agent/pi-web-search-lite/config.json` carries the tracked defaults - the exa provider, `deferred` activation, 3 results, 4000 inline characters, 100 inline lines and spilling to a file - the user's own values in that file win over the tracked ones, and a rerun changes nothing. (from pi-web-search/S2)
- **R16** WHEN the live web-search configuration is not valid JSON, THEN it is backed up and left untouched. (from pi-web-search/S3)
- **R17** WHEN the Pi configuration is installed, THEN no search credential appears in a tracked file, the key is read from the environment, and a missing `EXA_API_KEY` is reported without failing the install. (from pi-web-search/S4)
- **R18** WHEN Pi starts with the tracked base settings, THEN it installs the declared package and the extension's `web_search` and `web_fetch` tools are discoverable through `tool_search`. (from pi-web-search/S5)
- **R19** WHEN the installer sets Pi up, THEN the tracked Pi base declares the `npm:pi-lens` package at user scope, so Pi installs it at its next start and it loads in every project, and a live settings file with other packages keeps them all. (from pi-lens/S1)
- **R20** WHEN the installer sets Pi up, THEN `~/.pi-lens/config.json` carries the tracked stance - pi-lens disabled (`lens.enabled: false`), the `typos` server disabled, format, autofix and actionable-warnings autofix off - the user's own values in that file win over the tracked ones, and a rerun changes nothing. (from pi-lens/S2)
- **R21** WHEN the live global pi-lens configuration is not valid JSON, THEN it is backed up and left untouched. (from pi-lens/S3)
